# 🚀 주요 기여 및 기술적 해결점

## 1️⃣ AOP 기반 관리자 권한 체크 시스템 설계

### 배경

- 서비스 특성상 아티스트/공연 등록 후 관리자 승인이 필수인 구조로, 관리자 권한 검증이 핵심 비즈니스 로직이었습니다.

### 문제점

- 관리자 권한 체크 로직이 컨트롤러마다 중복 작성됨
- `if (memberRepository.findById(memberId).isAdmin())` 형태의 검증 코드 반복
- 권한 체크 방식이 일관되지 않아 누락 가능성 존재
- 신규 관리자 API 개발 시마다 보안 로직을 매번 작성해야 하는 비효율

### 해결 과정

**1) AOP 기반 공통 처리 방식 도입**

- `@AdminOnly` 커스텀 애노테이션 정의
- AOP Aspect에서 해당 애노테이션 감지 시 사전 권한 검증

**2) 검증 로직 구현**

- JWT 토큰에서 현재 로그인 사용자 ID 추출
- `MemberRepository`를 통해 관리자 여부 확인
- 권한 없을 경우 `ForbiddenException` 발생

**3) 도메인 로직 분리**

- 권한 검증 책임을 도메인 외부(AOP)로 추출
- 컨트롤러는 요청 흐름에만 집중

### 성과

- **관리자 API 10개 이상에 일관된 보안 정책 적용**
- **권한 검증 중복 코드 100% 제거 (if문 2줄 × 12개 메서드)**
- **신규 API 개발 시 보안 누락 리스크 제거**
- **컨트롤러 가독성 향상 및 유지보수성 개선**

## 2️⃣ 2단계 회원 가입 플로우 설계 및 데이터 무결성 보장

### 배경

- 선호 장르, 아티스트 정보 등 입력 항목이 많아 사용자 이탈 가능성이 높은 상황이었습니다.
- 이탈 방지를 위해 가입을 2단계로 분리하되, 1단계만 완료한 유저가 재접속 시 끊김 없이 2단계를 이어가도록 설계가 필요했습니다.
- **기술적 과제**
    - "불완전한 상태"의 데이터를 정의하고, 이메일 중복 방지와 데이터 무결성을 어떻게 유지할 것인가?

### 요구사항

- 1단계: 이메일 중복 확인 + 비밀번호 설정
- 2단계: 선호 장르 등 개인정보 입력 + 전화번호 인증
- 2단계 완료된 회원만 로그인 가능
- 이메일 중복 허용 X (최종 회원 기준)
- 1단계만 하고 나간 유저가 로그인 시도 시, **개인정보 입력 페이지로 자동 이동**

### **기술적 도전 및 의사결정**

> **1단계만 완료한 "불완전한 회원"을 어떻게 저장할 것인가?**
> 

**고려한 방안:**

1. 회원 테이블에 NULL 허용 하여 저장
    - 1단계에서 개인정보 컬럼 null인 상태로 회원 생성 → 2단계에서 update
    - 문제점:
        - 회원 테이블 내 이메일 UNIQUE 제약조건 제거 필요 → 무결성 깨짐
        - 회원 테이블에 "불완전한 데이터”를 저장해야 함
            - 필수 값(이름 등)에 NULL 허용 필요 → 제약조건 약화
        - 모든 회원 관련 로직에 “임시 회원 유무” 추가 검증 필요 → 비즈니스 로직 복잡도 증가
2. **임시회원 테이블 분리** ✅ (채택)
    - 1단계: 임시회원 테이블에 이메일/비밀번호만 저장
    - 2단계: 회원 테이블로 마이그레이션
    - ✅ 이점:
        - 이메일 UNIQUE 제약 유지, 명확한 상태 구분
        - 명확한 상태 구분
            - TempMember = 1단계만 완료 (불완전)
            - Member = 2단계까지 완료 (완전)
        - 이메일 UNIQUE 제약조건 완벽히 유지 가능

**구현 내용:** 

1.  **임시회원/회원 도메인 분리**
    - **임시회원**: 이메일, 비밀번호만 보유 (불완전한 상태)
    - **회원**: 개인정보 포함 (완전한 상태)
    - 소셜 로그인도 동일한 플로우 적용
2. **전화번호 인증 (Redis 활용)**
    - 무작위 인증번호 생성 → Redis 저장 (TTL 3분)
    - SMS 발송 → 사용자 입력값 검증
    - DB 배치 부담 없이 TTL 자동 만료 활용

### 성과

- **데이터 무결성 100% 유지 (이메일 UNIQUE 제약 보존)**
- **중간 이탈 후 재진입 시 자연스러운 UX 제공**
- **Redis TTL 활용으로 인증번호 관리 부담 제거**
- **명확한 회원 상태 구분으로 비즈니스 로직 단순화**

## 3️⃣ 도메인 중심 예외 처리 구조 설계

### **배경**

- 프로젝트 초반, `IllegalArgumentException` , `RuntimeException` 등 포괄적 예외만 사용하면 향후 도메인별 예외 구분이 어렵고, 클라이언트 응답 일관성이 떨어질 것으로 판단했습니다.

### 해결 과정

1) 계층적 커스텀 예외 설계

```java
// 상위 예외
InvalidException
NotFoundException  
DuplicateException

// 도메인별 예외 (상속)
DuplicateMemberException extends DuplicateException
NoSuchRegionException extends NotFoundException
```

2) 전역 예외 핸들러 구현

- `@RestControllerAdvice`로 상위 예외 일괄 처리
- HTTP 상태 코드 + 에러 코드 + 메시지 일관 응답

### **성과**

- **예외 발생 시 도메인/로직 추적 용이**
- **클라이언트 에러 코드 기반 대응 가능**
- **디버깅 및 테스트 속도 향상**
- **예외 처리 기준 통일**
